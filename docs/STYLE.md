# Style guide

This applies to everything written in this repository: code, comments, docstrings, commit messages, PR descriptions, ADRs, README, and the write-up. The reader is a colleague who is busy and competent.

## Voice

Write the way a senior engineer writes a design note to a teammate. Direct, specific, unhurried. State the fact, give the reason when the reason is not obvious, stop.

Good: "The loader uses COPY because row-by-row inserts took 40 seconds per hour of data."

Not good: "In order to ensure optimal performance, the loader leverages PostgreSQL's COPY command, which is a robust and efficient way to bulk-load data."

## Words and phrases to avoid

These are reliable markers of machine-written prose and they add nothing. Do not use them.

- it's worth noting, it is important to note, note that
- in order to (use "to")
- leverage, utilize (use "use")
- robust, seamless, comprehensive, powerful, cutting-edge, state-of-the-art
- delve, dive into, unpack, explore (as a verb for explaining)
- ensure that (usually "make sure" or just restructure)
- a wide range of, a variety of
- this allows us to, this enables
- as mentioned earlier, as discussed above
- overall, in summary, in conclusion (just end)
- any sentence that begins with "Great question" or addresses the reader's feelings

## Punctuation

- Commas, periods, colons, semicolons, parentheses. That is the set.
- No em dashes and no en dashes, anywhere, including YAML comments, SQL comments and commit bodies. If you want a dash, you want a comma, a colon or a new sentence.
- Hyphens only inside compound words (bare-earth, link-hour, pre-commit).
- No emoji. No decorative Unicode.
- Straight quotes in code and docs. Curly quotes are fine only in the write-up if the editor inserts them.

## Attribution

- No "Generated by", "Co-authored-by", "AI-assisted" or product names in commits, comments, code or docs.
- The one place the agent workflow is described is `CONTRIBUTING.md`. Everything else is silent on who typed it, with two exceptions: the `Agent:` commit trailer and the `Author:` line that opens a PR.
- Agent identities are their specialty names (`ingest-eng`, `terrain-rf-eng`). They appear in the commit trailer, the PR first line, ADR "proposed by" fields and `docs/STATUS.md` owners. Nothing else identifies them.

## Code

- Names: full words, no abbreviations except universally known ones (`db`, `id`, `utm`, `dem`, `snr`, `rssi`). A variable holding metres ends in `_m`; decibels `_db`; degrees `_deg`; seconds `_s`.
- Functions do one thing and are under 40 lines; if a docstring needs "and", split the function.
- Type hints on every signature. `mypy --strict` on `terrain/` and `pipeline/`.
- Comments say why. A comment that restates the code is deleted in review.
- No commented-out code. Git has it.
- No TODO without an issue number. `# TODO(#42): ...`.
- Module docstring: one paragraph on what the module is for and what it deliberately does not do.

## Docstrings (Google style)

```python
def fresnel_clearance_pct(profile: Profile, frequency_hz: float, h_tx_m: float, h_rx_m: float) -> float:
    """Minimum clearance along the path as a fraction of the first Fresnel radius.

    Args:
        profile: Terrain profile in EPSG:26915 with distance_m and elevation_m arrays.
        frequency_hz: Carrier frequency in hertz.
        h_tx_m: Transmitter antenna height above ground in metres.
        h_rx_m: Receiver antenna height above ground in metres.

    Returns:
        A value in [-inf, 1]. 1.0 means the first Fresnel zone is fully clear;
        0.0 means the terrain touches the direct ray; negative means obstructed.

    Raises:
        ValueError: if the profile has fewer than two samples.
    """
```

## SQL and dbt

- Lowercase keywords, snake_case identifiers, one clause per line.
- CTEs named for what they contain, not what they do (`direct_packets`, not `filter_step`).
- Every model has a `description` in its YAML and every column that a human will query has one too.
- Every model has at least `unique` and `not_null` tests on its grain key.
- Singular tests are named `assert_<what_must_be_true>.sql`.

## Commits

Conventional commits. Subject line imperative, under 72 characters, no trailing period. Body only when the subject cannot carry the why.

```
feat: land raw MQTT deliveries as hourly Parquet partitions

The in-memory buffer flushes on 5 minutes or 5000 messages, whichever
first. Partitioning by received hour keeps the loader's COPY batches
under 50 MB and makes replaying a single hour trivial.
```

Every commit ends with one trailer, separated from the body by a blank line:

```
Agent: ingest-eng
```

That is the only trailer. Git recognises it (`git log --format='%h %(trailers:key=Agent,valueonly)'`), and it is the per-commit record of which specialty did the work. Author and committer are always Casey.

## Pull requests

The first line is `Author: <agent>. Reviewer: reviewer.` Then four parts, in this order, each a short paragraph or a few bullets, then the run report verbatim.

- What: the change, in one or two sentences.
- Why: the reason, with a link to the plan section or ADR.
- How verified: the tests added, the manual check performed, the numbers observed.
- Not done: what was deliberately left out and where it is tracked.

If a test was skipped on purpose, say so under "Not done" with the reason.

## Documentation in docs/

- Written for the project owner first, a hiring reviewer second.
- Define a term on first use. Link the second use to the definition.
- Prefer a worked example with real numbers over a general description.
- Keep each doc under 1500 words. Split rather than scroll.
- ADRs follow `docs/adr/0000-template.md`.

## Logging

- `structlog`. Bind `component`, `asset` or `service`, and a `run_id` where one exists.
- One log line at the start and end of every external interaction with its duration.
- Levels: debug for per-record detail, info for per-batch progress, warning for recoverable anomalies you chose to continue past, error for failures that stop the unit of work.
- Never log secrets, raw payload bytes, coordinates at full precision for a known node, or unhashed node ids.

## Error handling

- Catch the narrowest exception that you can act on. Bare `except:` is a review block.
- Add context when re-raising: `raise LoaderError(f"copy failed for {path}") from err`.
- If you swallow an exception, log at warning with the reason it is safe, and count it in a metric or an asset check so it is visible.
- Validate inputs at the boundary (settings, decoded payloads, file headers), not deep inside pure functions.
- Dagster assets raise on failure; retries are declared on the asset with a backoff, never looped by hand.
