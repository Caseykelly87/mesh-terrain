# ADR 0006: Add ITU-R P.1812 through Py1812 beside ITM, behind one path-loss function

Date: 2026-11-14
Amended: 2026-11-15 (PR #24 comment 6894674840)
Status: accepted
Proposed by: terrain-rf-eng
Decided by: Casey

## Context

Phase 3 of `docs/PLAN.md` adds a fifth model beside free space, knife edge, Okumura-Hata and ITM (ADR 0002): ITU-R P.1812, run through the Python package Py1812 pinned to a git commit. The lead's brief of 2026-11-14 puts six questions to this ADR, drawn from the Phase 3 Stack table and Tasks line of `docs/PLAN.md` and from `.claude/agents/terrain-rf-eng.md`. Contract row `ter_06` adds a seventh, the Okumura-Hata threshold. Terms, defined once:

- ITU-R P.1812 is the International Telecommunication Union's method for predicting loss over terrain from 30 MHz to 6 GHz. Like ITM it reads the ground profile between the antennas; unlike ITM it also reads a clutter height at every profile point. Version 8 (September 2025) is current.
- Clutter is what stands on the ground between the antennas: buildings and trees. Its height is the surface height minus the bare-earth height. P.1812 calls it R, the representative clutter height, in metres at each profile point.
- Leaf-off and leaf-on: deciduous trees are bare (leaf-off) from about November to April and in leaf (leaf-on) from about May to October. Leaves hold water, which absorbs and scatters a 915 MHz signal, so a tree in leaf costs more signal than the same tree bare.
- The ITU digital maps are two world grids at 1.5 degree spacing that ship as text files with the Recommendation. DN50.TXT gives DN, how fast the air's refractive index falls over the lowest kilometre, which sets how much the atmosphere bends a signal back toward the ground. N050.TXT gives N0, the refractivity at sea level. P.1812 uses N0 only for tropospheric scatter: signal scattered back down by small irregularities in the air high above the horizon, which matters only on paths of tens to hundreds of kilometres. P.1812 reads both grids at the path's midpoint. At St. Louis DN is 39.1, an effective earth radius factor of 1.33, the same 4/3 the plan sets for our line of sight code. The maps are "an integral part of the recommendation and may not be reproduced, by any means whatsoever, without written permission of ITU" (the wording Py1812 repeats in its build script), so they are never committed, baked into an image or published.
- Basic transmission loss is the loss between two ideal antennas with no gain; transmit power and antenna gains are not in it. Every model below returns this quantity.

The spike (`docs/adr/0006-spike/`) installed Py1812 at the recommended commit in a scratch environment and repeated the 2026-11-08 test call with the maps kept outside the installed package. On a flat inland 10 km path at 915 MHz with 2 m antennas, P.1812 gives 149.48 dB, ITM 151.76 dB (ADR 0002) and free space 111.68 dB. A call takes 2 to 3 ms on a 1 001-point profile and 16 to 18 ms on a 10 001-point one.

## Options

### 1. How Py1812 is installed and pinned

Py1812 (github.com/eeveetza/Py1812, Ivica Stevanovic, Swiss Federal Office of Communications) has no PyPI release and no tags. On 2026-11-14 the head of `main` is still 6c9061dd (2026-08-28, "Fix for Issue #11"); the repository is active and has no open issue. The licence lets anyone use, modify and redistribute the code, asks for a dated notice on changes and an acknowledgement, and the author confirmed it as MIT or BSD style in issue #13.

1. A uv git dependency, `py1812 @ git+https://github.com/eeveetza/Py1812@6c9061dd`. Advantage: the plan's wording; `uv.lock` records the commit. Cost: uv runs the `git` program for a git source (tested: "Git executable not found"), and the Dagster image has none, so the image gains git plus a certificate line for the Norton secret.
2. A uv archive dependency at the same commit, `py1812 @ https://github.com/eeveetza/Py1812/archive/6c9061dd022e93c84169059a016643926ce89964.tar.gz`. Advantage: no git anywhere; `uv lock` records the archive's sha256 (`03d7c5bd...`, tested in a scratch project) and `uv sync --frozen` checks it, the pattern the Dockerfile already uses for ITM. Cost: GitHub builds archives on request, so a change on GitHub's side fails the install on the hash until someone updates the lock, the same risk STATUS records for ITM and H3 core.
3. A vendored copy of `P1812.py` (3 180 lines) under `terrain/`. Advantage: no download at install, and the map loading can be rewritten. Cost: third-party code in the repo outside ruff and mypy, a dated notice per edit, and each upstream change merged by hand; upstream changed the file four times in 2026 (two fixes, #9 and #11 with #13; one feature, the Gtx and Grx gains; and the update to P.1812-8).

Options 1 and 2 build Py1812 from source with `flit_core`, which its `pyproject.toml` asks for as `>=3.2,<4`; the spike's build used 3.12.0. Per PyPI, as read by the reviewer on 2026-11-14, 3.12.0 (2025-03-25) is the last 3.x release and the current release is 4.2.0, which Py1812's own `<4` already excludes, so the range resolves to 3.12.0 today. This project pins its own build tool exactly (`hatchling==1.27.0`, `pyproject.toml` line 34), and `flit_core` is not on Casey's list of downloads left unpinned (PR #21 comment 6886413798). Either:

- a. pin it with `[tool.uv] build-constraint-dependencies = ["flit-core==3.12.0"]`. Advantage: one line, matches hatchling, and a new flit_core release cannot change the build. Cost: a manual bump if Py1812 ever needs a newer flit_core.
- b. accept the range and add it to the unpinned list. Advantage: nothing to maintain. Cost: a new download pinned only to a range.

### 2. Where the maps live, and how the engine, the image and CI get them

Py1812 loads `P1812.npz` when it is imported, from its own installed folder (`P1812.py` line 19), and raises `FileNotFoundError` naming the site-packages path when the file is missing. The maps contribute only two numbers to a call, DN and N0 at the path centre, and `bt_loss` accepts both as arguments; passing them gives the same 149.48 dB (spike). Any option also has to meet `docs/INTERFACE.md`: the engine reads only the config, the snapshots it names and the layers it names (line 15); no defaults are hidden in code (line 19); and the same config, seed and snapshots give the same `content_sha256` (line 88). So the maps have to be a snapshot that the config names, not an environment setting.

1. Upstream in place: copy the two text files into the installed package's `maps/` folder and build the npz there. Advantage: no code of ours. Cost: every environment, worktree and image needs the step again; an image built this way carries ITU data, which becomes redistribution the day an image is pushed (Phase 6); and the maps sit outside the config and the run manifest, against INTERFACE.md line 15.
2. A map snapshot named in the config, a placeholder import, DN and N0 passed on every call.
   - `make p1812-maps` downloads the public zip (636 KB, sha256 `d3a51f29...`) into a snapshot `itu-r-p1812-8-202509` under `SNAPSHOTS_DIR`, holding the zip and its two text files. The manifest follows `snp_01`: id, download date, source URL, ITU's licence sentence and the sha256 of each file. The snapshot is registered in `raw.snapshot` like every other. No npz is built.
   - The engine config names the snapshot in `snapshots` whenever `models` lists `p1812`, so its `manifest_sha256` goes into the run manifest. The Dagster feature asset takes the map snapshot id in its run config and resolves it under `SNAPSHOTS_DIR`, as `ingester/assets.py` line 63 does for the capture (through a `snapshots_dir` setting that `pipeline/common/settings.py` does not have yet; see Consequences), and records the id and the manifest sha256 in its materialisation metadata, so `features.link_prediction` can be traced to its maps (`snp_01`). No environment setting names the maps on either path.
   - `terrain/p1812.py` imports Py1812 once, at module level, so Python's import lock serialises it. It first refuses with `RuntimeError` if `Py1812.P1812` is already in `sys.modules` or a `P1812.npz` exists in the installed package folder. It then patches `importlib.resources.files` for the length of the import, so the one map load reads a placeholder built in memory: the patched `files("Py1812")` returns an object whose `joinpath` hands back an `io.BytesIO` holding `np.savez(DN50=nan, N050=nan)`, two 1 by 1 grids of NaN (not a number: the value a computer holds for a missing or undefined number). Nothing is written to disk or committed, so no file outside a snapshot manifest feeds production code and nothing in the repo is named like the maps. After the import, `P1812.files` keeps the replacement; that is harmless because line 19 is its only use.
   - Once per run, the wrapper reads the two text files from the named snapshot and checks each one's sha256 against the snapshot manifest. It raises `RuntimeError` naming `make p1812-maps` when the files are missing or do not match. It passes DN and N0 on every call, interpolated with Py1812's own `interp2` at the centre Py1812's own `great_circle_path` gives. A call that omits them would fall back to the placeholder and fail with `IndexError` (spike), never with a wrong number.
   - `path_loss_db` imports `terrain.p1812` on its first `p1812` call, and no module that the Dagster definitions or the asset import at top level imports it. Loading definitions therefore never runs Py1812's import or the patch, and `make check-definitions` and compose-smoke need neither the maps nor Py1812.
   - Advantage: upstream code untouched, nothing written into site-packages, an image or the repo, the import works without maps, and a run's maps are pinned in its manifest. Cost: the patch depends on how line 19 loads the maps. An upstream change there fails the import loudly, and only when we move the pin.
3. A vendored loader that takes a path, with option 1.3: Py1812's map load moved into a function that takes the folder. Advantage: no patch of the standard library, so it is the choice that cannot break on an upstream change. Cost: those of option 1.3.

Options 2 and 3 need one change to `docs/INTERFACE.md`, which is lead-only: the lead makes it after Casey decides. The `snapshots` row would read: "ids of the snapshots to use: DEM always; DSM source (EPT project) and canopy optional; the OpenStreetMap buildings snapshot optional, and required when `models` lists `hata`; the P.1812 map snapshot, or the synthetic map fixture, required when `models` lists `p1812`. Without the OpenStreetMap snapshot, `tx_building_draws` and `rx_building_draws` are null, never zero, and `hata_variant` is null. Each id is a folder with its manifest present; the engine needs no database row." The manifest needs no new field, since the map snapshot appears in its `snapshots` list.

CI has no maps and no network for the engine fixture run. Under option 2.2 the CI fixture config names a committed synthetic map snapshot, `p1812-maps-synthetic`, among the engine fixtures: the two text files at full grid size (about 90 KB and 120 KB), holding the made-up constants DN 40 and N0 325, not ITU data, with a manifest that says so. Its id in a run manifest tells a reader the P.1812 numbers are not real. The unit tests use the same fixture. On the host, `make check-p1812` repeats the 149.48 dB call against the real snapshot, as `make check-itm` does for ITM. Upstream also ships ITU validation profiles (`tests/validation_profiles/`), and its `tests/validateP1812.py` passes each profile's own DN and N0 (lines 247 to 248), so the profiles need no maps. That script imports `matplotlib.pyplot` (line 18), outside the stack, so CI runs the profiles through our own test, which reads them with `P1812.read_sg3_measurements2` and calls `bt_loss` through the same import. They come from ITU-R Study Group 3's measurement database, and their licence has to be checked before any of them is committed or fetched in CI. Fetching the zip in a CI step was considered and rejected: it puts itu.int's availability into every CI run and tests nothing the synthetic fixture does not.

### 3. One function for every model (sketch)

```python
Model = Literal["fspl", "knife_edge", "hata", "itm", "p1812"]

@dataclass(frozen=True)
class PathProfile:
    """Ground and clutter along one straight path, EPSG:26915."""
    distance_m: FloatArray          # from tx, ascending, starts at 0, uniform step
    ground_m: FloatArray            # metres above NAVD88, no earth curvature applied
    clutter_m: FloatArray | None    # metres above ground; None where only the metro DEM exists
    tx_xy_m: tuple[float, float]    # easting, northing
    rx_xy_m: tuple[float, float]

def path_loss_db(
    model: Model,
    profile: PathProfile,
    frequency_mhz: float,
    tx: AntennaProfile,             # engine/profiles/<name>.yaml: height_m, gain_dbi, polarisation
    rx: AntennaProfile,
    *,
    hata_variant: Literal["urban", "suburban"] | None = None,
    p1812_maps: P1812Maps | None = None,   # DN50 and N050 grids from a verified map snapshot
) -> float | None:
    """Median basic transmission loss in dB, antenna gains excluded."""
```

- It returns None only for `p1812` without clutter (question 4). It raises `ValueError` for a zero-length path, fewer than five samples, or `hata` without a variant. It raises `RuntimeError` naming the install step when the ITM library is missing or `p1812` has no maps. Amended by item 11 (PR #30): fewer than five samples is refused with reason `short_profile`, not `ValueError`.
- The profile carries ground heights without curvature. ITM and P.1812 apply their own effective earth radius; knife edge, line of sight and Fresnel apply k = 4/3 inside `terrain/`. A curved profile fed to ITM or P.1812 would count the bulge twice. The agent file's cross-check would catch it: compare knife edge with ITM and P.1812 on a dozen real links, and treat any gap over 10 dB on a clear line of sight path as a units or heights bug.
- The Phase 3 Tasks line of `docs/PLAN.md` says "profile with earth curvature k = 4/3 using windowed reads". This ADR replaces that wording: the profile sampler returns uncurved ground, and the k = 4/3 bulge is applied by line of sight, Fresnel and knife edge only. The lead amends PLAN.md with Casey after the decision.
- Units change at the model edge only: MHz to GHz and metres to km for P.1812, metres to km for Hata, and the endpoints from EPSG:26915 to EPSG:4326 through one pyproj transformer for P.1812's latitude and longitude inputs. No arithmetic on degrees.
- Endpoint sampling sits outside: the sampler calls the function once per draw and model and keeps the median and interquartile range.

Transmit power and antenna gains (Casey's addition A, 2026-11-14):

- The engine never applies them. It predicts basic transmission loss, and its calibration input is already a loss (`observed_loss_db`, `docs/INTERFACE.md` line 32), so whoever holds an RSSI converts it to a loss first. In this project that step is the Phase 4 validation (analytics-eng): observed loss = transmit power + transmit antenna gain + receive antenna gain - RSSI, with the relayer as transmitter and the gateway as receiver. Phase 4 is where predictions meet observations, and keeping power out of the engine keeps its predictions free of any assumption about the radios.
- Values, from the `mesh_node` profile at both ends (decision 5.1): 22 dBm transmit power by default, 0 dBi at each antenna, no cable loss. The profile has no cable-loss field, so the 0 dBi is taken as net of cable.
- Why 22 dBm, since transmit power is not in the data:
  - Meshtastic's default `tx_power` is 0, meaning "default max legal continuous power" (`config.proto`, meshtastic protobufs 2.7.11).
  - Firmware v2.7.11.ee68575 turns 0 into the region limit, 30 dBm for US (`src/mesh/RadioInterface.cpp` line 32 and lines 587 to 588).
  - `limitPower` (`RadioInterface.cpp` lines 664 to 684) then subtracts `TX_GAIN_LORA` and clamps to the chip maximum: 22 dBm by default for the SX126x radios (the `#ifndef` default in `src/mesh/SX126xInterface.cpp` line 18) and the LR1110, and 20 dBm for the older SX127x (`src/mesh/RF95Interface.cpp` line 16).
  - Board files can override the chip value. At this tag 13 `variant.h` files define `SX126X_MAX_POWER`: 12 active and one commented out (`nrf52_promicro_diy_tcxo`, 8). Ten set 22; Station G1 sets 16 and Station G2 19, to drive an external amplifier whose gain the firmware does not record. `variants/esp32s3/heltec_v4/platformio.ini` line 11 sets `SX126X_MAX_POWER=11` for the Heltec V4 (`hw_model` 110), a chip feeding an amplifier with no `TX_GAIN_LORA`. The RadioMaster 900 Bandit and Bandit Nano lower the SX127x value to 10 and 12 dBm (`RF95_MAX_POWER` in their `variant.h`). `TX_GAIN_LORA` is "PA gain + antenna gain (if variant has a non-removable antenna)" (`src/configuration.h` lines 83 to 85). It is defined only in the module blocks of `configuration.h` lines 88 to 118: E22-900M30S (7 dB), E22-900M33S (25 dB), NiceRF MiniF27 (7 dB), NiceRF F30 HF (8 dB) and NiceRF F30 LF (10 dB). Those five blocks also set `SX126X_MAX_POWER`: 8 for the E22-900M33S and 22 for the other four. No `variant.h` defines `TX_GAIN_LORA`.
  - A node left at its defaults therefore sends 22 dBm on most SX1262 boards and 20 dBm on an SX1276 board. A board with an amplifier radiates more than its chip setting, and any node sends less if its owner set a lower power.
  - Casey kept the flat 22 dBm on 2026-11-15 (item 3 under Decision).
- The 0 dBi is the profile's round value from `docs/INTERFACE.md`; no node reports its antenna.
- What absorbs an error: in the mixed model, a relayer's random intercept takes up a constant error in that relayer's power and antenna gain, and a gateway's takes up its antenna gain, cable loss and receiver offset. The single-model baselines have no per-node term, so a power error shared by all nodes shows as bias, which Phase 4 reports beside RMSE and which adds to RMSE.
- The test: the Phase 4 sensitivity table adds transmit power rows at 20 dBm and 30 dBm against the 22 dBm default, the SX127x chip limit and the US limit.
- Left open: LoRa decodes below the noise floor (negative SNR), where the RSSI a radio reports includes the noise as well as the signal. Contract row `lnk_06` admits SNR down to -30 dB, so how those receipts are treated decides which receipts are validated. That is Casey's decision, asked with the analysis design question before Phase 4 (STATUS, Known issues).

### 4. Clutter as P.1812's R

Clutter height at each profile point is max(DSM minus DEM, canopy height where the canopy is nonzero), from the 1 m layers. The DSM (digital surface model) is the first-return lidar surface, the tops of roofs and trees. Every collection over the MSA that the USGS lidar index (WESM) dates is recorded as leaf-off. The St. Louis 2017 collection under the test tile was flown in February 2017. Corridors elsewhere may use other EPT projects; those with recorded dates were flown between March 2014 (IL_MadisonCo_2014) and March 2024 (IL_10CoNRCS_D23), per `docs/measurements-2026-11-08.md`. MO_FranklinCo_2011 and the legacy 2010 to 2015 projects have no recorded date or leaf state. IL_19County_D24, flown to March 2026, has no EPT yet, so it supplies no DSM. The capture ran on 22 to 25 October 2026, with the trees mostly still in leaf. A leaf-off lidar pass sees a deciduous tree as bare branches: some pulses return from the branches, many reach the ground, so DSM minus DEM understates the tree. The Meta and WRI canopy height map comes from satellite imagery, about 80 percent of it from 2018 to 2020 and 40 to 68 percent of it leaf-on (`docs/measurements-2026-11-08.md`). Taking the larger value keeps buildings from the lidar and each tree at the taller of its two estimates. Three limits remain and go in the write-up. Both layers are mostly years older than the capture. A height says nothing about how dense a crown is, which is what leaves change. And P.1812 treats clutter as an obstacle to bend over, not foliage to pass through.

Py1812 adds R to every profile point except the two terminals (`g = h + R`, then `g[0] = h[0]` and `g[-1] = h[-1]`), so a 2 m antenna beside a 15 m tree sees the tree one sample away.

1. Where only the metro DEM exists, `p1812` is null. Advantage: matches "clutter null, never zero"; P.1812 with R = 0 is a second bare-earth model, which ITM already provides. Cost: if the corridors are cut (plan cut order item 2), P.1812 covers only the test tile's links.
2. Where only the metro DEM exists, run P.1812 with R = 0 and label it. Advantage: a P.1812 number on every link. Cost: a label column, or a separate R = 0 column, changes `docs/INTERFACE.md`, the `link_prediction` data model in `docs/PLAN.md` (line 82) and `docs/schema.md`. Reusing the `p1812` column for R = 0 values changes its meaning, which is a major `schema_version` bump.

Under option 4.1 the engine refuses a config that lists `p1812` and names neither a DSM nor a canopy snapshot, so a run cannot produce an all-null column by accident.

### 5. Antenna profiles for validation

1. `mesh_node` (2 m, 0 dBi, 22 dBm) at both ends, as the plan says. Advantage: nothing in the capture says which gateways stand on masts. The Phase 4 mixed model also gives every relayer and every gateway a random intercept: a constant per node that the model estimates from the data, so a node that is always 6 dB stronger than predicted gets its own +6 dB instead of spreading that error over every link. That absorbs a constant offset per node (power, gain, cable). Cost: a tall gateway's height gain changes with distance, so part of it stays in the residual; the Phase 4 rows at 1 m and 5 m show how much.
2. `mesh_node` at the relayer and `site_gateway` (10 m, 3 dBi) at the gateway. Advantage: right for the gateways that are on masts. Cost: a guess applied to every gateway, most of which are home nodes like any other.
3. A height per node from its reported altitude minus the DEM. Advantage: a measured height for each node. Cost: GPS altitude errors of tens of metres and hand-entered altitudes make it worse than a fixed guess.

Sensitivity rows (Casey's addition B, 2026-11-14): besides 1 m and 5 m at both ends, the Phase 4 table adds a 10 m antenna at the gateway end with the relayer at 2 m. ITM and P.1812 accept 10 m; Okumura-Hata stays below its 30 m base range. The row uses 0 dBi, so it changes height only (item 4 under Decision, 2026-11-15).

### 6. P.1812 settings

The plan fixes none of these. `.claude/agents/terrain-rf-eng.md` (line 27) names p = 50 and the inland zone, and the rest are Py1812 defaults. Recommended as fixed values:

- p = 50, the time percentage: the median, and the top of the 1 to 50 range Py1812 accepts.
- Zone 4, inland, at every point. The MSA's rivers and lakes are far smaller than the water bodies P.1812 treats as sea.
- Location percentage pL = 50 with sigmaL = 0, so the result is also the median over locations.
- Distance to the coast dct = dcr = 500 km. Py1812 uses these distances only when they are 5 km or less (`P1812.py` lines 663 to 671, the over-sea duct coupling term), so 500 km keeps that term off; the nearest sea coast is about 1 000 km away.
- DN and N0 passed on every call from the map snapshot, as question 2 describes.
- flag4 = 0, so the terrain profile is used; debug = 0, because debug mode writes a CSV into the working directory. Item 2 (a) under Decision changes this to debug = 1 with an in-memory log.
- Polarisation from the antenna profile (vertical). Transmit power and gains stay at their defaults: they enter only the field strength output, and we read the loss.

ITM keeps the settings of ADR 0002. Choices the plan leaves open, with a recommendation each:

- R per profile point as measured, or a representative value per land class (Py1812 ships class tables, one for NLCD, which the plan dropped). Recommend per point: it is what the plan's clutter rule describes.
- A negative DSM minus DEM floored at 0; it comes from lidar noise, the small random error in each lidar height, which on bare ground puts DSM minus DEM a little above or below zero instead of exactly zero. The floor is applied before the maximum. `ter_05` already requires non-negative clutter, so this reads the rule rather than changing it, but the clutter rule is Casey's.
- A point where the DSM has no value but the DEM does, mostly water, which returns no lidar pulse. Py1812 does not fail on a NaN in R, and Lb comes back finite with no warning. The NaN enters `g = h + R` (`P1812.py` line 330). At most points the comparisons after it skip that point, as though it had no clutter. At the first interior point, index 1 next to the transmitter, it does worse: Py1812's `dl_bull` (lines 1819 to 1846) takes its largest slope with Python's built-in `max`, which returns NaN when the first element is NaN, every test after that comes out false, and the knife-edge loss for the whole path is 0. In spike run 3, on the flat 10 km path with R = 10 m everywhere (160.17 dB), a NaN at index 300 or 999 changes nothing, and a NaN at index 1 gives 137.36 dB, below even the bare-ground 149.48 dB. On a hilly profile (190.23 dB with R = 10 m, 176.55 dB bare) a NaN at index 1 also gives 137.36 dB, 52.87 dB too low. Where the skipped point is the one obstacle that sets the loss, the obstacle vanishes: a single 30 m clutter point at index 500 gives 159.74 dB, and the same point as NaN 149.48 dB. So a NaN is skipped, except at the first interior point, where it removes the path's diffraction loss, and the wrapper has to fill or refuse every NaN in R before it calls `bt_loss`. Recommend clutter 0 at a point where the DSM has no value and the DEM has one, unless the canopy is nonzero there, with the count of filled points kept per link; any NaN left after that raises `ValueError` (item 11 under Decision replaces that exception class with its own; the rule itself is unchanged). This is also part of the clutter rule.
- The profile step: P.1812 gets the profile every model gets, 10 m on the metro DEM and 1 m on the 1 m layers. At 16 to 18 ms a call, 150 link-hours times 16 draws at 1 m take under a minute. Item 1 (b) under Decision replaces this with a 10 m P.1812 profile on the 1 m layers.

Clutter at the endpoints (Casey's addition C, 2026-11-14):

- P.1812-8 section 3.2 says "The height of clutter should not be added to the terrain heights at the transmitter and receiver", so the first and last surface heights are terrain heights (equations 1d and 1e). Py1812 does the same (`g[0] = h[0]` and `g[-1] = h[-1]`, `P1812.py` lines 330 to 332). In the spike, 8 m of clutter at the transmitter point alone leaves 149.48 dB unchanged at both 10 m and 1 m steps.
- P.1812-8 has no separate terminal clutter loss. Equation (63) combines troposcatter with diffraction and ducting. The legend to equation (69) still describes Lbc as "including the effects of terminal clutter losses", but no equation in version 8 computes one. Py1812 has none either; it dropped its clutter-category argument `Ct` in February 2026. Clutter near a terminal acts only through the profile, as an obstacle at the intermediate points beside it. In the Recommendation, R at the receiver also scales location variability (section 4.7, equation 65), which has no effect at pL = 50; Py1812's `bt_loss` ignores R there, and equation (65) lives only in its `stdDev` helper, which `bt_loss` does not call.
- A pixel is one 1 m square of the 1 m layers. An antenna below the clutter height at its own pixel, such as a 2 m antenna whose endpoint draw lands on an 8 m roof, is therefore modelled standing 2 m above bare ground at that point, with the clutter of the neighbouring profile points in front of it: a node beside a building, not on or in it. P.1812-8 says building entry loss (Recommendation ITU-R P.2040) should be added for a terminal inside a building: for the transmitter in Annex 1 section 1, and for the receiver through Lloc = Lbe, equation (67b), with section 4.8 giving the loss. We add none, because nothing says which nodes are indoors.
- A building pixel is a 1 m DEM pixel whose centre lies inside an OSM building footprint: the same footprints `ter_05` and the Hata threshold use. They come from an OpenStreetMap snapshot registered under `snp_01`, as Casey asked (PR #24 comment 6887814186): id `osm-geofabrik-mo-il-<extract date>`, holding Geofabrik's dated extracts for Missouri and Illinois, `https://download.geofabrik.de/north-america/us/missouri-YYMMDD.osm.pbf` and `https://download.geofabrik.de/north-america/us/illinois-YYMMDD.osm.pbf` never the `-latest` files. Geofabrik keeps its daily files only briefly, so a daily URL will stop resolving; the snapshot takes the latest first-of-month file (for example `missouri-261101.osm.pbf`), which stays listed longer. Both files must carry the same date, which becomes `<extract date>` and the manifest's `capture_date`. ### 7. The Okumura-Hata variant threshold (`ter_06`)

Okumura-Hata is Hata's empirical formula fitted to Okumura's measurements around Tokyo, valid for 150 to 1 500 MHz, 1 to 20 km, base antennas 30 to 200 m and mobile antennas 1 to 10 m. Both variants use the mobile antenna correction for a small or medium city, a(hm) = (1.1 log10(f) - 0.7) hm - (1.56 log10(f) - 0.8); St. Louis is not a large city in Hata's sense, and the large-city form differs by 0.25 dB at 2 m. The suburban variant is the urban one minus (2(log10(f/28))^2 + 5.4) dB, which is 9.96 dB at 906.875 MHz. With 2 m at both ends every link is below the base antenna range, so Hata is extrapolated everywhere; it stays as a baseline with the antennas as given, not clamped to 30 m, and the results say it is out of range.

1. Urban when the mean of the two endpoints' building footprint shares within 100 m is at least 0.20, suburban otherwise. Each endpoint's share is the median over the draws, so a link-hour has one variant. Advantage: both ends count equally, as the loss does. Cost: a link from a dense block to a sparse suburb falls on whichever side of 0.20 the mean lands.
2. Urban when either endpoint reaches the threshold. Advantage: one end in a dense block, such as a downtown gateway, makes the link urban. Cost: that one end outweighs a suburban other end.
3. Urban when both do. Advantage: urban only when the whole link is built up at both ends. Cost: few links outside downtown qualify, so the variant would hardly vary.

The 0.20 is reasoned, not measured: as a rough figure, blocks of detached houses cover 10 to 20 percent of their ground with buildings, row houses and commercial streets 30 percent or more. The engine brief measures the shares at the link endpoints from the OSM snapshot and reports how many link-hours change variant between 0.15 and 0.25 before the value is used.

Cost: one new column, the two models that never read a profile lose draws they could have computed, and contract rows `ter_01`, `ter_02`, `ter_05` and `ter_06` change (Consequences).
   - (c) Refuse per model: only the models that need the missing value are null for that draw, each with its own count. A DEM gap refuses every model whose profile reads it; a cell with no value or a NaN in R refuses only P.1812; free space and Okumura-Hata always keep the draw. Advantage: every number that can be computed is kept. Cost: one count column per model, and each model's median comes from different draws. Draws are not stored, only each row's median and interquartile range, so nothing downstream can undo that. Contract rows `ter_01`, `ter_02` and `ter_05` change (Consequences).
   - Recommend (b), with canopy gaps filled as (i). Every model's median comes from the same draws, the count shows how often refusals happen, and it costs one column.
   - Decided: (b) with (i). A canopy pixel with no value counts as canopy 0, no trees, so the clutter there is DSM minus DEM; it is set to 0 before step 4 of item 6 (a), not left to a comparison with NaN. Every other refusal drops the draw for every model, counted per link-hour row in one column, `refused_draws` (Consequences). Each engine run report gives the count of canopy no-data pixels per tile and per corridor; there is no column for it.
   - Measured in spike run 7 (`docs/adr/0006-spike/spike_dem_nodata.py`, 2026-11-15): the x72y429 1 m DEM file on TNM (`USGS_one_meter_x72y429_MO_SaintLouis_2017.tif`, ETag `"7d4013fa90919a36b190a9e98ff8d13f-93"`, 483 356 883 bytes, Last-Modified 2026-02-13), streamed in windows with nothing kept: 10 012 by 10 012 pixels in EPSG:26915, nodata -999999, and 0 nodata pixels. So with this file the x72y429 run meets no DEM gap. Run 7 reads the live TNM file, not a registered snapshot, so the engine unit counts again on the snapshot it registers. The metro 10 m DEM, the corridor tiles and the DSM and canopy layers are unmeasured.
   - Amended on 2026-11-15 by Casey on PR #30 ("2: refusal for a too-short profile is a fourth cause under ADR 0006 item 11. Each engine run report breaks refused draws down by cause (missing map data, empty 10 m cell, missing clutter, too-short profile). No new column."). A fourth cause: a too-short profile, one with fewer samples than a model needs, which is no interior sample for line of sight, Fresnel and knife edge and fewer than the five samples of decision 3 for `path_loss_db`.
